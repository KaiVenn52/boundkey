# CLOCK IN win strategy

BoundKey should be judged as a **mobile financial-control product**, not as a cryptography library.

## Stickiness / PMF

The recurring loop is: agents discover paid tools → user gets a permission request → phone authorizes/monitors the capability. The app's long-term role is the financial remote for multiple agents, not a one-time setup screen.

Proof to show:

- QR request from a real desktop agent flow;
- active capability card;
- recent activity / blocked attempts;
- no new agent wallet to seed or top up.

## UX

The judge should understand the request before hearing protocol terms:

**Codex → Research API → max $0.50 → one session key.**

Only after approval do we reveal MPP / Payment Channels.

## Innovation

Do not pitch “spending sessions” as new. The new product move is **cross-device signer separation**:

- wallet/payer authority on Solana Mobile;
- client voucher/session authority on the agent machine;
- official Payment Channels program connects them.

This is a mobile-rooted capability system for agents.

## Presentation

The winning 90-second arc:

1. “Would you paste your wallet private key into Codex?”
2. Agent hits paid research service.
3. QR appears.
4. Phone: max $0.50, one payee, one agent key.
5. Wallet approval.
6. Paid stream runs automatically.
7. Prompt injection asks for $5 / redirect.
8. Visible blocked result.
9. “Give the agent a key. Not your wallet.”

## What not to spend demo time on

- AP2 theory.
- generic x402 explanations.
- long architecture diagrams.
- market-size claims about current agent commerce.
- AI risk scoring.

## Judge proof bundle

Have these open in tabs before judging:

- Android APK installed and working.
- 90-second video locally downloaded.
- GitHub README at architecture section.
- one real explorer transaction / channel id.
- test output showing voucher format/signatures.
- offline web demo as network fallback.
